# Hearth — Changelog

Detailed entries for the newest ~10 versions. Older entries live in `HEARTH-archive.md`.

**Do NOT read this file end to end at session start** — read only the entries for the versions you are actually touching. Architecture and working notes are in `HEARTH-notes.md`; pending work is in `HEARTH-backlog.md`.

## ✍️ How to write an entry (added 16/08/2026)

Entries here had grown to 500–2,800 words each, written by the most expensive model at the end of the longest context in the session — and the detail was already in the PR, which is permanent and searchable. New entries are capped:

- **A headline sentence** — what changed, and the date, in the existing bold style.
- **Up to ~150 words** of substance: the mechanism, the non-obvious decision, the test that pins it.
- **Every "do NOT simplify this into X" warning**, in full — these are the entries' real value and are exempt from the cap.
- **A link to the PR** for the full reasoning. Do not reproduce the PR body here.

If a change genuinely needs more (a shipped incident, a new subsystem), write the long version in its own doc and link it, as `HEARTH-freeze-analysis.md` and `HEARTH-global-search.md` already do.

## Recently completed (newest ~10 versions — older detailed entries live in `HEARTH-archive.md`)

- **v517: the startup update check no longer leaves an unhandled promise rejection (09/11/2026).** Found in a cross-project review: `reg.update()` after `serviceWorker.register` had no `.catch`, so a check that failed (no signal) or was cancelled (worker unregistered mid-check) raised an unhandled rejection. Invisible in production, but in the test suite `resetSW` unregisters between cases and the stray rejection failed `04-sw-cdn-cgi-passthrough` on slower machines (every run in one cloud session; CI had been passing by timing). Fix: `reg.update().catch(function(){})`. Nothing else about registration, update or the banner changed; `sw.js` changed only for the version line. No test files changed.
- **v516: Projects — every section folds, one at a time or all together (07/11/2026).** Asked by Cathal. In a project's detail each section header (the ungrouped Tasks and Links, and every named group) is now a button that folds or opens that section, with ▲ open / ▼ folded. A **Collapse all / Expand all** button sits above the sections when there are two or more, using the Lists rule: if any section is open it collapses all, otherwise it expands all. Folds are remembered **per project, per phone** in `fl4_proj_folds` (`{projectId: {"t:task"|"t:link"|"g:<groupKey>": 1}}`). Like `fl4_catOpen_*`, that key is device-local UI state, not synced and not in the backup. Deleting a project drops its entry. **Do NOT move fold state into `fl4_projects`**: it would sync, so folding on one phone would fold the other, and every fold would stamp the record. Pinned by `tests/cases/95-project-folds.js`.
- **v515: Projects — tasks are numbered and can be reordered (07/11/2026).** Asked by Cathal. Open tasks show 1, 2, 3… within their group; **↕ Reorder tasks** puts ↑/↓ on each one. Confirmed: done tasks still sink to the bottom, numbering restarts per group, links keep their own sort. New item field `order` (number or ""). A group follows due dates until its first move, which numbers its open tasks 1..n (`projMoveTask`); after that a move rewrites **only the moved task**, giving it the midpoint between its new neighbours, and renumbers once only if the gap is tied or worn out. A new task, or one moved by its Group field, joins the end (`projOrderForJoin`). An imported plan is ordered from the start, in file order. **Do NOT renumber the whole group on every move**: the item merge is newest-wins per task, so two phones each rewriting n tasks would sync into a mix of both orders. Pinned by `tests/cases/94-project-task-order.js`.
- **v514: a soft halfway tone on long timed holds (07/11/2026).** Asked by Cathal. Confirmed: **halfway only** (not 10s-left), a **single soft tone** (440 Hz, quieter and shorter than the 3-note end chime so it never reads as "pose over"), for holds of **60 seconds or more** (`HALFWAY_MIN_SEC`). Applies to yoga poses (`startYogaTimer`) and timed physio holds (`togglePhysioTimer`); workout rest is not an exercise and stays silent. `isHalfwayTick(dur, remaining)` fires when the countdown reaches `floor(dur/2)`, so it plays exactly once per hold, also after a pause/resume. Pinned by `tests/cases/93-halfway-tone.js`.
- **v513: Projects — group suggestions as chips, and long project notes fold (06/11/2026).** Spotted by Cathal on his phone. (1) The item editor's Group field offered existing groups through a native `<datalist>`, whose Android popup turns near-transparent once you type. It is now a row of tappable chips under the field (`.proj-grp-chip`), filtered as you type (contains, any case), with the exact current value hidden; tapping fills the field. (2) Project notes over 260 characters or 6 lines start folded to ~5 lines with a fade and a **Show more ▼ / Show less ▲** toggle (`_projNotesOpen`, per project, session only — like `_projShowDone`). Short notes are unchanged. **Do NOT go back to a `<datalist>`** — its popup can't be styled on Android.
- **v512: import a plan into Projects, item groups, and Quote/Cost/Contact retired (06/11/2026).** Asked by Cathal, starting from his US passport and citizenship plan. Confirmed: **Projects ⋯ › Import a plan**, which works like the golf course import (copy prompt → AI chat → paste `project-v1` JSON → preview → **Create project**). Every import makes a **new** project. Items get an optional free-text **group**. The detail shows ungrouped items first, under their type headers as before, then each group with an "N of M done" count. **Quote, Cost and Contact are retired**: costs, quotes and contacts now go in the notes. Items of those types already saved stay in the data but are never shown, counted or searched (`projItemShown`). The "€ spent" total is gone with them. **Do NOT drop retired items from the data or map them to tasks.** Pinned by `tests/cases/92-project-import.js` and the retired-type block in `85-projects.js`. v511 was taken by open PR #283.
- **v510: choose the voice and speed for Full Body Flow's spoken cues (24/10/2026).** Asked by Cathal. Confirmed: a **dropdown of the phone's installed English voices** (plus "Phone default"), **Slow / Normal / Fast** (0.75 / 0.9 / 1.1), and a **Test** button that says the first pose. These rows show only while Spoken cues is on, and both choices are remembered on this device. The app can only use voices the phone has; more can be downloaded in the phone's settings (iPhone: Accessibility → Spoken Content → Voices; Android: Text-to-speech → Install voice data). Chrome loads voices late, so a `voiceschanged` listener repaints the intro. **Do NOT build an utterance outside `yogaUtterance()`**: it is the one place the voice and speed are applied. Pinned by `tests/cases/91-yoga-voice-picker.js`.
- **v509: Full Body Flow — a Short version and spoken cues (24/10/2026).** Asked by Cathal ("start with Full Body Flow"). Confirmed: Short = **fewer poses at normal holds** (15 poses, ~12 min — keeps warm-up, core, cat, bird dog, child's pose, low lunges, mountain, Warrior II, bridge, supine twists, savasana); voice = **pose name + the short cues**, not the Details paragraph. Intro gains a **Session · remembered** box (Length Full/Short, Spoken cues On/Off); the running screen has a Voice on/off button. Speech uses the browser's on-device `speechSynthesis`, one utterance per cue (Chrome cuts long ones off), silenced on pause/close and re-read on resume. A short session saves as "Full Body Flow (short)". Each Warrior II now opens with its own stance cue (Codex on #279: Short goes Mountain → Warrior II with no Warrior I, and the Right→Left switch was never cued in either flow). **Do NOT give Short its own pose array** — it is `inShort:true` on `YOGA_FB_BASE`, so the reviewed/original switches still apply. **Do NOT move speech into each advance path** — `yogaSpeakIfDue()` derives it from `SS.ySpokenFor`. Pinned by `tests/cases/90-yoga-short-voice.js`.
- **v508: the top ‹ on a workout's start screen no longer asks "Progress will be lost?" (07/10/2026).** Spotted by Cathal on Beginner Pull Day: the intro's Cancel closed straight away but the header ‹ (`sesBackBtn`) confirmed, because its workout guard fired in every phase except `complete`. It now skips `intro` too: nothing is logged before Start. Mid-workout the confirm is unchanged. Yoga already confirms only while running; physio never does. Test `89-workout-intro-back.js`. **Do NOT drop the confirm for the `log`, `rest` or `cond` phases** — leaving there really does discard the logged rounds.
- **v507: Beginner Pull Day and Beginner Push Day (07/10/2026).** Asked by Cathal for his wife, a beginner with no hernia or back history; he will log her sessions on his phone for now. Two new Train cards (General fitness) and `WK_TRAIN.pullb` / `.pushb`: Ring Rows + Goblet Squat, Assisted Dead Hang (timed) + Glute Bridge; Incline Push-ups + Romanian Deadlift, Bench Dips (bent knees) + Side Plank (knees). 2 rounds per superset, 90s rest, plain beginner cues with a "harder later" step each, and their own note (`WK_BEGINNER_NOTE`: stop 2–3 reps short, progress one thing at a time — shown in a light cream box via `noteLight`; Pull/Push Day's safety note — and the yoga, physio and Pull-up Plan (`.pu-warn`) caution boxes — moved from the dark box to a light amber one (`#FCEFD6`, 14px dark text) in the same version, keeping the ⚠️; the note offers no "extra round", as the rounds are fixed) and conditioning (`COND_BEGINNER`, picked by `wktCond()`). The intro line now reads rounds and rest from the data instead of a hard-coded "3 rounds · 90s". Test `88-beginner-days.js`. **Do NOT give these days `WK_TRAIN_NOTE` or merge them into a level on Pull/Push Day** — his clinical text would mislead her.
- **v506: Favourites in Recipes ordered by most-opened, then A–Z (06/10/2026).** Asked by Cathal; he chose **opening a recipe** as the "use" signal (over planned/marked-cooked). Every open from the recipe list or the meal plan's "Open recipe" adds 1 to `fl4_recipe_opens` (`{recipeId: n}`). The Favourites filter sorts by that count, highest first, with ties broken by name (case-insensitive). All, category and search views keep their old order. **Do NOT move the count onto the recipe record.** The store is device-local: it isn't synced or exported, and each phone orders by its own use. A field on the recipe would need `r.updated` bumped on every open, and in the newest-wins recipe merge, just viewing a recipe would then overwrite the partner's real edit. Pinned by `tests/cases/87-recipe-fav-order.js`.
